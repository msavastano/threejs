# Taste
- Prefers modern, non-deprecated library APIs — explicitly demands current releases and forbids deprecated constructs (e.g., Three.js r128+ via ES-module import map, `BufferGeometry` only, no `THREE.Geometry`). Confidence: 0.9
- Wants clean, well-commented code — asks for "clean, well-commented" vanilla JS with sectioned comments explaining each subsystem rather than bare code dumps. Confidence: 0.9
- Prefers self-contained, single-file deliverables for demos/prototypes (e.g., one HTML file with inline CSS/JS, CDN imports, runnable by just opening it) — states this emphatically ("DO NOT USE ANY OTHER FILES") and requires third-party libraries (physics engines, Three.js addons) to be pulled from CDN import maps rather than local installs or extra asset/module files. Confidence: 0.85
- Expects rendered/visual output to be verified empirically before delivery: load the page in headless Chrome (`--headless=new --screenshot --dump-dom`), inspect the screenshot plus the page's own error surface/console dump instead of trusting untested shader/host code — and re-run the same verification loop after every fix until clean. When browser automation is unavailable, fall back to lighter static checks: extract the inline `<script type="module">` block and `node --check` it, grep for known corruption-artifact patterns, and re-run the checks after every fix. Confidence: 0.8
- Works on Windows: commands must be cmd.exe/PowerShell-compatible (no bash syntax); when quoted paths containing spaces fail through the shell layer, fall back to space-free temp-dir staging, batch files, or PowerShell. Treats silent/empty command output as ambiguous — verify the expected side effect (staged file exists, exit status, echoed sentinel like `SYNTAX_OK`) before trusting a pass, and when cmd.exe silently drops a compound command, redo the whole step end-to-end in PowerShell. Confidence: 0.9
- Cares about performance-conscious implementation: typed-array data layouts (`Float32Array`), minimal per-frame GPU work — avoid CPU↔GPU round-trips entirely where possible (no per-frame `readRenderTargetPixels`; bind render-target textures directly to materials, using a stable display RT refreshed by a cheap copy pass, and compute palettes on-GPU in linear space), single `needsUpdate` per frame, zero-allocation animation loops that reuse pre-created scratch objects (an `Object3D` and `Color` mutated in place; never `new Matrix4`/`Vector3` per instance per frame), numerical-stability guards (damping factors, speed clamps, force softening), and — in GPU/shader code — march-step budgets, bounding-volume early exits, and DPR caps (e.g., `Math.min(devicePixelRatio, 1.5)`) to bound fragment cost. Confidence: 0.85
- For graphics/shader requests, wants feature-complete, quality-tuned render pipelines — e.g., Fresnel-weighted metal reflections, SDF soft shadows, ambient occlusion, plus a post stack (tonemap/exposure, fog, vignette, dither) — not minimal proof-of-concept stubs. Confidence: 0.75
- Wants GLSL and Three.js host-API integration that actually works under strict rules — validate rather than assume: GLSL side, no `const` initializers from non-constant expressions (e.g. `length()`) and every referenced helper/uniform declared before use; when patching materials via `onBeforeCompile`, injected helper functions that sample built-in uniforms must be placed *after* the chunk that declares them (a function using `map` injected after `<common>` fails to compile because `<map_pars_fragment>` — where `map`/`vMapUv` are declared — comes later; inject after `<map_pars_fragment>` instead); Three.js side, declare every ShaderMaterial uniform in the constructor (never assign `.value` on an undeclared uniform entry), match CPU readback buffer types to the render target's internal type (half-float target ≠ Uint8Array), respect per-stage built-ins (`normalMatrix` doesn't exist in fragment shaders), and reset the render target after every off-screen pass (`renderer.setRenderTarget(null)` inside the shared pass helper) — otherwise the next main-scene `renderer.render()` silently draws into whatever RT was last bound (black canvas plus read/write feedback loops, no console errors). Confidence: 0.85
- Matches the workspace's established conventions instead of imposing a new setup — reads existing sibling files/demos first and mirrors their stack, file layout, and naming (confirmed pattern: single-file HTML demos, import map pinned to three@0.160.0, dark mono HUD, banner-commented code/shader sections). Note: mirroring *conventions* is welcome, but this does not license reusing or deriving from existing code when the spec says to write an own implementation. Confidence: 0.85
- When a freshly written file comes out with corruption/garbled lines, prefers a full clean rewrite over piecemeal patches, followed by an artifact grep sweep and a syntax re-check (`node --check` on the extracted module script, temp file cleaned up afterward) before declaring done. Confidence: 0.7
- In Three.js mechanism/animation scenes, wants the mechanics genuinely simulated — linkages solved per-frame against real world transforms (rotating crank pins, conrod stretch/orientation via matrixWorld, rigging ropes anchored to Object3D markers) rather than faked/keyframed motion, with the math verified. Confidence: 0.55
- Keeps coupled subsystems mutually consistent (shader disk-noise rotation direction matched to the particle swarm's orbital direction, sign conventions re-derived when a mismatch is suspected). Confidence: 0.65
- Prefers instanced rendering for many similar objects in Three.js — a single `THREE.InstancedMesh` with `DynamicDrawUsage` over thousands of individual `Mesh` objects, per-instance gradient colors written via `setColorAt()` into an explicit `InstancedBufferAttribute` on `instanceColor` with `instanceColor.needsUpdate` flagged each frame colors change — and wants instancing kept "where practical" even in physics scenes: rigid bodies/colliders created lazily on first simulation trigger so pre-simulation frames stay pure instancing, then per-frame matrix sync from body transforms via `setMatrixAt`. Confidence: 0.85
- For effect/visual shaders (e.g. energy shields), wants the full quality recipe wired in by default: Fresnel rim (`pow(1.0 - dot(N, V), k)` in world space so it stays correct under rotation), animated procedural noise (3D value-noise FBM sampled in world coords with multiple scrolling layers, plus optional UV scanline overlay) all driven by a `uTime` uniform, a smooth `sin(uTime*speed)` breathing pulse modulating both color and alpha, `THREE.AdditiveBlending` + `transparent: true` + `depthWrite: false` + `side: THREE.DoubleSide` so the effect is visible from inside and out and never self-occludes, and `uTime` updated each frame via `THREE.Clock` inside the RAF loop. Confidence: 0.8
- When the target file already exists, reads it first and verifies it against the stated requirements before changing anything; if the existing implementation already satisfies every requirement, reports "no rewrite needed" with a requirement-by-requirement checklist rather than overwriting working code. Confidence: 0.7
- For Three.js physics work, names the engine explicitly and expects a canonical game-loop architecture rather than a naive `world.step()` inside the render callback: fixed timestep (1/60) driven by an accumulator, `requestAnimationFrame` used only for rendering, prev/cur pose snapshots per body blended with `alpha = accumulator / dt` (`lerpVectors` for position, `slerp` for quaternion), plus a spiral-of-death guard (clamped frame delta, capped steps per frame, backlog shed rather than carried). Static boundary colliders (floor with its top face exactly at y=0, wall colliders parented to one fixed container body) and a spawner keyed to *simulation* time so its cadence is frame-rate free are part of the expected baseline. Enclosed arenas (ground plane plus surrounding walls, visuals matched by static colliders) and body counts in the ~1,000 range are the expected scale, with "prioritize both visual quality and performance" as a standing instruction — realistic rigid-body behavior (falling, colliding, piling up naturally) must not come at the cost of frame rate. Confidence: 0.75
